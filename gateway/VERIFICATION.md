## Current protocol and remaining checks

`POST /v1/describe {"text":"1/2 cup beans, 100g rice\n2 fl oz milk"}` returns `mode=usda_assisted`, exact `original_text`, `review_required=true`, ordered `foods` envelopes with `input_text`, `query`, `quantity_hint`, `unit_hint`, `unit_recognized`, `quantity_estimated`, `match_estimated`, `match_status`, `needs_details`, and projected USDA `food` or null. Nonempty item count must be retained even on no match. Generic descriptions search Survey/FNDDS; normal USDA search remains available for other datasets or branded foods. No quantity/density is invented, no sources combine nutrients, and every proposed item requires manual review.

Direct read of [Nutritionix developer homepage](https://developer.nutritionix.com/) succeeded using standard-library urllib after the web reader returned 402; its published notice states public free-access tier is no longer maintained. Therefore the implementation makes zero Nutritionix network requests, ignores all legacy env settings, excludes it from gateway status, and rejects `/v1/parse`, `/v1/nutritionix/describe`, `/v1/nutritionix/parse` with HTTP 403/free_only. This is stronger than an account-entitlement toggle.

The official [USDA guide](https://fdc.nal.usda.gov/api-guide/) confirms public-domain/CC0 data, key privacy, GET search/details and request limits; [USDA's key service](https://api.data.gov/signup/) provides the free key path. Use an existing key only; no account was created. Two authorized read-only DEMO_KEY calls were attempted, both to search for milk: one with multiple data types, one with only Survey/FNDDS. Both returned HTTP 400 (the second body was a generic nginx Bad Request page). No retries, third request or detail call were made. The cause of those earlier failures was not established. This earlier engineer limitation is superseded for host authentication/search/details by the parent's two subsequent HTTP200 reads, documented in [release validation](../releases/VALIDATION.md). Broader coverage, live Survey/FNDDS description query behavior, actual Android phone networking and optional gateway TLS/proxy deadlines remain unverified; no paid hosting is a dependency.

[Open Food Facts official introduction](https://openfoodfacts.github.io/openfoodfacts-server/api/) confirms read operations require no authentication beyond identifying User-Agent; current product read limit is 15/min/IP. OFF attribution/ODbL/DbCL subset/export rules remain preserved. Owner contact URL/email in custom User-Agent remains to be provided before broader distribution.

The parser accepts bounded separated item phrases, not arbitrary natural-language prose, conjunctions, recipes or commas in product names. Unknown leading unit words are preserved in both hints and search terms because they may instead describe food. Named portions only convert through explicit source definitions. Absent quantity stays null; unmatched food stays null/unknown until reviewed. A failure other than missing detail/no match aborts the whole action with a safe error; already-started free calls may finish and consume quota. Four concurrent workers/global slots and the 60-second client read limit improve latency but do not certify total wall-clock deadlines against trickle traffic.
