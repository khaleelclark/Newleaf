# Free sources, mappings and published licenses

Provider policy for Newleaf 0.1.5. Documentation reviewed October 22, 2026; initial provider checks were October 1. No account was registered, subscribed, paid for or deployed. Two historical authorized header-only official USDA search/detail reads returned HTTP200; see [release validation](../releases/VALIDATION.md). Public response fixtures contain catalog data only, without credentials. This is an implementation decision record, not a legal certification.

- USDA: [API guide](https://fdc.nal.usda.gov/api-guide/) documents authenticated search/details, key privacy, the default 1,000/hour/IP limit and CC0/public-domain data. [Branded documentation](https://fdc.nal.usda.gov/GBFPD_Documentation/) explicitly defines either 100 g or 100 mL according to submitted serving units, and distinguishes missing from zero. Non-branded supported datasets use per-100-g; branded data requires an explicit mass or volume serving unit. Incomplete search summaries carry UNKNOWN/null normalization and request selected details; details with unknown basis are rejected. Source item IDs are `usda:{fdcId}`. Core mapping uses USDA nutrient IDs; units are checked, and extra nutrients retain provider ID/unit. Energy can use explicit kJ or Atwater energy nutrient values when kcal is missing; no calories are invented from macro totals. FoodData Central attribution accompanies snapshots/exports.

- Open Food Facts: [current introduction](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/) identifies v3.6 as current and v2 as deprecated, requires an identifying User-Agent and states separate reuse licenses. The truthful default is Newleaf/0.1.0 (personal Android food journal); a constructor override supports the owner's chosen contact URL/email, which is still unprovided and should be added before broader distribution. The current introduction lists product read limit 15/minute (per IP for server calls, per user for direct mobile calls); Newleaf performs one explicit read per action, with duplicate in-flight suppression. [v3 API schema](https://github.com/openfoodfacts/openfoodfacts-server/blob/main/docs/api/ref/api-v3.yaml), [nutrition v3 schema](https://github.com/openfoodfacts/openfoodfacts-server/blob/main/docs/api/ref/schemas/product_nutrition_v3.yaml), and [nutrient values schema](https://github.com/openfoodfacts/openfoodfacts-server/blob/main/docs/api/ref/schemas/nutrient_values_v3_base.yaml) describe the new nutrition `input_sets`, explicit `per` (100g/100ml/serving), preparation, units and values. The implementation pins `/api/v3.6/product/{code}.json` and selects one supported nutrient-bearing as-sold set, preferring manufacturer then packaging among nutrient-bearing candidates; metadata-only sets do not outrank usable nutrients. It preserves explicit same-origin label servings and normalized whole-package size; it deliberately ignores `aggregated_set` because that combines sources. No legacy flat-nutriments fallback and no guessed liquid basis. No packaging/manufacturer set or unknown basis with nutrition yields unsupported data; a product with no nutrition can still provide an exact identity with unknown nutrients. Source IDs are `openfoodfacts:{barcode}`; GTIN check digit plus exact/zero-padded equivalence protects product identity. This supports GTIN-8/12/13/14, not arbitrary internal store codes or UPC-E. HTTP 404/explicit product-not-found is a true no-match; no keyword fallback. Source region comes from provider country tags, never from phone locale. No product images are fetched. Nutrient comparisons (<, > etc.) are not treated as exact numeric values. Salt/sodium conversion (salt/2.5) and available carbohydrate+fiber total are marked derived and preserve original provider fields. `value_computed` is not silently substituted for supplied nutrition.

- USDA-assisted descriptions: `POST /v1/describe` splits up to eight comma/newline item descriptions and matches each through USDA GET search plus selected detail. Survey/FNDDS search favors generic prepared foods with household portions; normal USDA search still covers other datasets and branded foods. All matches and parsed quantities are provisional/estimated, the full original input and each fragment are preserved, and review is mandatory. Missing matches remain editable unknown candidates. A supported unit label does not imply a known portion mass; unsupported conversions and unspecified quantities stay unknown. There is no paid language-model/API dependency or automatic journal save. USDA attribution/CC0 accompanies matched reference values; no-match placeholders explicitly say no database record was matched.

- Nutritionix is **disabled permanently in the active free-only APIs**. The [official developer homepage](https://developer.nutritionix.com/) checked directly on October 1 states its public free-access tier is no longer maintained; access enquiries go through its sales team. Newleaf makes zero Nutritionix requests regardless of legacy credentials/rights flags. Old public routes return `free_only`, configuration ignores commercial variables, and status does not advertise it. The existing Kotlin normalizer/fixtures remain for historical data import only; they confer no new rights or active capability. Historical records retain their original account/license evidence rather than being relabeled as USDA or assumed unrestricted.

USDA's [official key service](https://api.data.gov/signup/) offers a free API key and its [API guide](https://fdc.nal.usda.gov/api-guide/) publishes CC0/public-domain data, a default 1,000/hour/IP limit and lower public DEMO_KEY limits (30/hour, 50/day). The primary Android client accepts the owner's existing personal key, sending it in X-Api-Key only to official USDA HTTPS. The data owner keeps it in a distinct Keystore vault and excludes it from Room/export/backup; recorded Keystore/restore isolation checks are in release validation; physical-phone acceptance remains open. Direct mode requires no hosting. Optional deployed/shared keys remain server-only. No new registration is authorized or performed. Open Food Facts reads are free and require only an identifying User-Agent, with published rate limits and licensing conditions. An optional self-hosted gateway on an existing machine has no paid hosting software dependency; HTTPS/token configuration remains necessary for phone access.

Open Food Facts personal-journal policy uses its [published licensing guidance](https://openfoodfacts.github.io/documentation/docs/Product-Opener/api/tutorials/license-be-on-the-legal-side/), [ODbL 1.0](https://opendatacommons.org/licenses/odbl/1-0/) and [DbCL 1.0](https://opendatacommons.org/licenses/dbcl/1-0/). ODbL permits temporary/permanent copying and derivatives subject to its conditions; notices/license URIs and share-alike/access requirements apply when conveying or publicly using covered data. DbCL grants content reuse subject to ODbL. On that published basis, the adapter now sets snapshotAllowed/exportAllowed=true, preserving attribution, database URL, both full license URIs and derivation evidence. No unspecified owner-review checkbox disables personal logging or export.

Exports must preserve source notices in JSON/Markdown/CSV/backups and provide an independent machine-readable OFF-derived nutrition subset under ODbL/DbCL, without private journal notes, photos, body measurements or activity. Personal material is separate collective content and is not automatically relicensed under OFF terms. This is the documented implementation policy, not a certification that every redistribution use is unrestricted. Product images have separate rights and are not fetched. Broad public catalogs or new distribution/combination uses require evaluating the applicable license obligations separately. The data/export implementation supplies that independent subset with source notices and integrity coverage; its API documents privacy exclusions and regression coverage.

No network credential, raw provider response cache, image or provider interpreted timestamp enters Entry. Original mapped numeric values/units, source references, basis, conversions, missingness, estimation and region are preserved in consumed snapshots. Sources never fill each other's nutrient gaps. Catalog refresh does not mutate any historical journal record. If provider rights cannot support Newleaf's required complete portable history, resolve that provider choice with the owner before claiming a complete release.
